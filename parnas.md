## 1.	Briefly describe one important lesson about modularity that the paper describes and that you think is still relevant today.
One important lesson from the paper is that modules should hide important design decisions from the rest of the program. Instead of organizing a system around the steps it performs, Parnas argues that each module should be responsible for one specific decision that might change later. I think this is still relevant today because it makes programs easier to update and maintain. If one part of a program changes, developers do not have to rewrite the entire system.

## 2.	Computing has advanced significantly since this paper was written. Briefly describe one challenge (not necessarily with modularity) or perspective that, while realistic in 1972, does not apply today.
One challenge discussed in the paper that is less important today is the concern over limited memory and storage. The paper spends a lot of time discussing how data should be packed and stored efficiently because computer resources were much more limited in 1972. While efficiency still matters, modern computers have far more memory and storage, so most programmers do not have to worry about those restrictions as much as developers did when the paper was written.

## 3.	Have you used modularity or information hiding in a previous CS course? Briefly describe where and how. If not, describe how you would apply it to a past assignment. 
Yes. In previous programming assignments, I have used modularity by separating my code into different classes and functions based on their responsibilities. For example, I would keep user input, data processing, and output in separate sections rather than putting everything into one large file. This made my code easier to read, debug, and update because changes in one section usually did not affect the others.
